# Five short grout attempts, November 4 at 11:05

All five attempts stopped on the independent 600 ms motor lease, with valid
line detections still arriving. This is a Pi control-loop regression introduced
by adding cookie tracking, distinct from the earlier 09:45 line-loss stop.

| First driving sample | Next sample gap | Minimum logged confidence | Stop reason |
| --- | ---: | ---: | --- |
| 11:05:20.418 | 673 ms | 0.983 | motion lease expired |
| 11:05:28.221 | 691 ms | 0.984 | motion lease expired |
| 11:05:33.282 | 722 ms | 0.950 | motion lease expired |
| 11:05:38.028 | 706 ms | 0.941 | motion lease expired |
| 11:05:43.516 | 738 ms | 0.933 | motion lease expired |

Each attempt logged only two drive samples, both showing zero run-relative
wheel distance. The second sample used a sensor snapshot taken before the
slow map work; this does not establish that the robot did not move. Line
frame ages in these samples were approximately 88–180 ms, within the guard.

The mission's target tick is 200 ms. Experiment mapping was performed before
the drive tick, repeatedly scanning all 9476 cookies, and could also invoke
synchronous JSON/fsync persistence. Sample gaps exceeded the lease duration.
There is no per-function timing trace on the Pi, so the logs do not separate
the cost of full-grid sweeps, persistence and other pre-drive work.

Build 3.1.grout.3 fixes the regression without extending the watchdog:

- Grout mode updates drive control directly, bypassing unrelated localization
  and destination work, then records the run map.
- Cookie coverage checks only the footprint's bounding cells. At the configured
  87 mm radius/pitch this is at most nine cells per point, rather than 9476.
- Active experiment map/coverage updates remain in memory. Ending the mode
  flushes the map; map.png still reads current in-memory state.
- Tests compare bounded coverage to a full-grid reference, check that active
  mapping does not persist, and retain independent motor-deadman checks.

A 1000-update host microbenchmark (pose plus one sweep, no disk I/O) measured
0.0074 ms median and 0.7625 ms maximum. These are development-Mac timings,
not Pi timings or a physical run validation.

## Wake/reset correction

The supplied log shows startup at 11:04:23, no boot bytes after the 15-second
capture, and Safe-mode verification only at 11:04:57. No runtime `reset`
command completion appears in this log; its exact blocking point cannot be
reconstructed from this recording.

The old reset could wait for the mission lock and I/O command owner before
emitting bytes. Build 3.1.grout.3 sends contiguous raw `80 07` hex immediately
from the request path, before either wait. No read, flush, logging, OI function
or sleep occurs before/between these bytes. Startup likewise sends this pair
as its first serial operation. The owner completes boot recovery afterward;
commands queued before reset are discarded, fresh sensors are required, and
the cancelled mission is not resumed.

The focused reset test deliberately leaves the owner stopped and confirms the
bytes are already written before letting reset completion run. Physical
asleep-device confirmation and a new grout run remain pending deployment.
